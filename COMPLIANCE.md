# Compliance statement — AI City Challenge 2026 Track 2, Team 24 (UIT–Kitchen)

## Data usage

- **Training and model selection use only the synthetic SynWTS set** (train/val
  splits): `mlcglab/synwts`, revision
  `9d6e7abce9a906e3e9bb6a2941dcce8b128654cf`. No real-world WTS
  training/validation videos and no models pre-trained on the WTS dataset are
  used anywhere in training.
- **Real-world WTS and BDD_PC_5K data are used for inference only**, on the
  official public-test package as distributed (videos, caption metadata, and
  the organizer-provided test bbox archives).
- **No manual annotation of test data and no manual rewriting of test
  outputs.** Every step from raw data to the two submission files is automated
  code in this repository.

## Models and revisions

| Model | Source | Revision |
|---|---|---|
| Qwen/Qwen3.5-9B (base for all LoRA adapters) | Hugging Face, public | `c202236235762e1c871ad0ccb60c8ee5ba337b9a` |
| nvidia/Cosmos-Transfer2.5-2B (restyles synthetic training frames only; never touches test data) | Hugging Face, public (gated) | `ce8440327c632d8313c3bde69db13b627ba5cae1` (distilled edge) |
| LoRA adapters (ours) | `artifacts/adapters/` (git LFS) | trained per this repo |

Python dependencies are pinned to exact versions in the `Dockerfile`; the
SynWTS dataset revision is pinned in the README download command. Known
residual nondeterminism (GPU LoRA training, unseeded DPO candidate sampling)
is covered by the expected-score band in README §4.

## Exact path producing the submission

`code/run_e2e.py` is the single entry point; the default run
(README §3, Option A or B) executes the stages

```
prep_test → prep_train → train_base → predict_base → predict_8bit →
compose_wsd2 → train_ctx → predict_ctx → predict_bundle → compose_vqa →
train_caption → predict_caption → stitch
```

and writes exactly `submissions/subtask2_vqa.json` and
`submissions/subtask1_captioning.json`. All intermediate probabilities are
regenerated by these stages — none are shipped.

Included in the repo but **not** on the submission path:

- the MBR best-of-N prediction branch (`QWEN35_PRED_NCAND > 1`) — the pipeline
  uses greedy decoding;
- the `*.sh` scripts — historical deploy pipelines kept for reference only.
  In particular `bundle_test_pipeline.sh` is the historical script whose logic
  now lives in the `predict_bundle` + `compose_vqa` stages, and
  `cosmos_night.sh` is the historical form of Option C
  (`cosmos_prep` + `train_bundle` stages).

## The bundle (Cosmos) adapter

Our submitted best VQA routes five question types through the
`vqa_lora_bundle` adapter (the pipeline default; `--no-bundle` disables it):

- The adapter was trained **only on SynWTS-derived data**: synthetic overhead
  train keyframes restyled with the public Cosmos-Transfer2.5-2B model plus
  photometric domain randomization. Restyled synthetic data remains
  synthetic-derived — no real-world WTS/BDD content enters training.
- Prediction with it is standard bf16 inference on the official test frames
  (`predict_bundle` stage); Cosmos is not involved at test time.
- The adapter ships in `artifacts/adapters/`; README §3 Option C reproduces it
  from scratch (the Cosmos restyle itself runs outside this image because the
  model is a gated repo with its own environment).

## Cosmos guardrails note

The historical restyle run (`cosmos_night.sh`) passed Cosmos's
`--disable-guardrails` inference flag. That step processed only our own
synthetic, rendered frames — no real-world imagery and no real persons appear
in them — and its outputs were used solely as internal training data for the
bundle adapter, which we consider the use-case-appropriate safeguard the
NVIDIA Open Model License asks for. The Option C reproduction instructions do
not use this flag: reproducers run Cosmos with its default guardrails.

## BDD_PC_5K

See the note in `README.md`: the submission answers every entry in the
official test files (77% of which are BDD_PC_5K); entries outside the scored
subset are ignored by the evaluator. No BDD data is used in training.
